# 42. Audit: repos, commitments, health checks, wake-ups (2026-11-16)

Kernel 7.3.4-1-cachyos, Noctalia 5.5.0 on Umbriel (test build), asusctl 6.5.0 + PR #404, on the charger. A sweep of everything left open: upstream items, the health check, timers, and what still wakes the machine at idle.

## Fixed

| Problem | Cause | Fix |
|---|---|---|
| **Boot health check alarmed on every boot**: "The SSD freeze fix did not build for kernel 7.3.4" | When 7.3.4 shipped the MTL016 fix, the DKMS package was retired, but the check still required a module under `updates/dkms/` | `g16-doctor` disassembles the kernel's `vmd.ko` and looks for the `_raw_spin_lock` call in `vmd_irq`, the mark of 7307899e381c. ## ROG Control 1.3.0 (community-plugins #1453)

The Noctalia maintainer's review (2026-11-15 23:00 UTC) found a blocking bug, and the PR was moved back to draft. `render()` collected the panel's sections in a table constructor where any section can be `nil`, and `ipairs` stops at the first `nil`. On laptops without a UPower charge limit, Display, Lighting and Sensors disappeared. Our 1.2.0 sync went out after that review without addressing it.

A fresh review of the whole plugin, checked against the Noctalia and asusd 6.5.0 sources, found 11 more issues. All are verified and fixed:

- **AMD models:** asusd's LowPower (3) shows and works as Silent; asusd aliases Quiet↔LowPower itself (`resolve_alias`). Custom (4) is shown by name. CPU temperature comes from `k10temp`. The GPU status line finds an AMD dGPU too: a non-boot display device, read through `boot_vga`, which needs no config-space access.
- **Re-enumeration:** Aura and Slash object paths include the USB device number, so the service now refreshes on `InterfacesAdded`/`InterfacesRemoved`.
- **asusd availability:**
  - When asusd leaves the bus (`gdbus`: "does not have an owner"), the panel says so at once.
  - A failed read is retried on the next tick.
  - A refused `runAsync`, which returns `false` and never calls back, no longer leaves a busy flag set for good.
- **Key presses and toggles:**
  - Repeat key presses step from the issued value. Live test: two quick `next-profile` presses went Balanced → Turbo → Silent; before, both started from Balanced.
  - A refused write rebuilds the toggles. The reconciler only re-applies `checked` when the value changes (`ui_tree_reconciler.cpp:2138`), so the toggles are now keyed on a failure count (`:980`).
- **Lighting effect:** if the current effect isn't offered, it is shown instead of a wrong "Static".
- **Battery:** only the system battery is used: UPower `PowerSupply=true`, and sysfs `scope` ≠ Device.
- **One profile write, not two:** asusd's `set_platform_profile_on_ac` and `..._on_battery` already call `set_platform_profile` (`ctrl_platform.rs:638-639`, `603-604`). Every write makes the firmware notify NVPCF, which wakes the dGPU.
- **Graphics switching through asusd:** offered only when it exposes `QueuedGpuValue`.
- **`props()`:** `value.data == false` used to come back as the wrapper table.
- **Match theme colour:** now opt-in, so nothing is written to the keyboard at startup.

Released as v1.3.0 and synced to the PR branch. The PR description is updated, the maintainer has a reply, and the PR is marked ready for review.

## Idle wake-ups, screen off and locked

Voluntary context switches per command over 30 s, sampled with one `awk` per snapshot. A first attempt forked per thread, and its own process churn inflated ananicy-cpp to 325/s.

| Source | Wake-ups/s | Note |
|---|---|---|

| tailscaled | 15.5 | |

| umbriel-test | 10 | |
| iwlwifi IRQ | 9.3 | |
| Everything | ~474 | ~320 without the audit tooling |

**Noctalia's main loop:** its thread sits in `poll(27 fds, ≤200 ms)`. One source with a 200 ms deadline is `LockKeysService` (`src/system/lock_keys_service.cpp`, `kRefreshInterval = 200ms`). It re-reads the Caps/Num/Scroll Lock LED brightness from sysfs whenever the lock-keys OSD or a lock-keys widget is enabled, and `osd.kinds.lock_keys` defaults to true. Sysfs LED `brightness` can't be polled for changes, which is why it loops.
- **Event-driven fix:** the compositor already knows the locked modifiers and could publish them over its IPC, which Noctalia subscribes to anyway.
- **Workaround:** turning the lock-keys OSD off saves ~5 wake-ups/s. Left on by preference.
- **Still unattributed:** the rest of the main loop's ~10/s. Noctalia's built-in profiler (`NOCTALIA_IDLE_PROFILE=1`) would attribute it, but it needs a shell restart.

**The four streams:** `umbriel subscribe`, KDE Connect `gdbus monitor`, and two from ROG Control (asusd, UPower battery). The pidfd PR (D17) takes each from 10/s to 1/s.

## Overnight unattended run (2026-11-16/17, on battery)

### Power button opens the power menu

`~/.config/systemd/user/power-key-menu.service` holds a logind `handle-power-key` block inhibitor (`systemd-inhibit ... sleep infinity`), bound to `noctalia.service`. While the shell runs, logind leaves the key alone and Umbriel's `XF86PowerOff` binding opens Noctalia's session menu. At the greeter, or if the shell is down, logind's default (poweroff) applies, and a 4 s hold still forces power-off in firmware. The binding is not active while locked: the lock screen has its own power buttons, and the press still wakes the display. A press that wakes the laptop from s2idle opens no menu, because the ACPI button driver sends no key while suspended. Still to do: a manual press test.

### Sleep on battery when idle

Noctalia had no idle sleep, so with the lid open the laptop stayed awake on battery all night. A new idle behavior, `sleep-on-battery`, does it (excerpt: `configs/home/.local/state/noctalia/idle-sleep-on-battery.toml`):
- **Trigger:** 900 s of idle runs `~/.local/bin/idle-sleep start`.
- **Watcher:** a transient user unit checks once a minute and calls `systemctl suspend-then-hibernate` when all of these hold:
  - the laptop is on battery;
  - no audio stream is uncorked (`pactl -f json list sink-inputs`; native PipeWire streams count);
  - nothing holds a logind `sleep` block (`ListInhibitors`).
- **Cancel:** activity stops the watcher.

Video players already block idle through Wayland. Tested: start and cancel, audio detection with `paplay` and `pw-cat`, and block detection with a test inhibitor.

### Num Lock kept the keyboard awake

After a driver reload the keyboard never autosuspended. `rpm` tracing showed usage count 0 with suspend attempts failing. `usbhid_suspend()` returns `-EBUSY` while any keyboard LED is lit (`hidinput_count_leds()`, `ignoreled=0`), and Num Lock was on.
- **Cause:** Umbriel's `numlock_toggle = true`, carried over from the niri config, switches Num Lock on for the session. The G16 has no numpad.
- **Fix:** set to `false`, and Num Lock was turned off with one synthetic `KEY_NUMLOCK` (uinput). The keyboard suspended within 2 s.
- **Detection:** `g16-doctor` now flags a lit Num Lock LED. The finding is in the asusctl #404 follow-up.

### Keyboard backlight kernel fix: tested

`hid-asus-wake-dkms` was installed and loaded live (`modprobe -r hid_asus && modprobe hid_asus`; the keymap and asusd's Aura object survived). Four LED-class brightness writes to the autosuspended keyboard:

| Module | Keyboard after each write | `-108` errors |
| --- | --- | --- |
| stock 7.3.4 (DKMS keeps it in `/var/lib/dkms/.../original_module`) | stayed suspended | 4 |
| patched | resumed, applied, autosuspended again | 0 |

The patch applies with zero offset to hid.git `for-next`, which doesn't fix this yet. It waits only for the author's Signed-off-by (`upstream/drafts/0001-...patch`).

### Battery A/B (D20)

On battery, screen on with the lock screen (static), backlight 486/512, dGPU asleep. Each condition had 90 s to settle and 240 s of `current_now × voltage_now` sampled every 2 s.

| Condition | Battery W | CPU package W | Note |
| --- | --- | --- | --- |
| idle, 240 Hz (1) | **6.53** | 1.67 | no GPU wake in window |
| idle, 60 Hz (1) | **6.64** | 1.68 | no GPU wake in window |
| idle, 240 Hz (2) | 7.33 | 1.67 | GPU wake just before |
| idle, 60 Hz (2) | 7.93 | 1.86 | GPU wake in window |
| light load (10% of a core in 30 ms bursts), turbo on | 8.10 | 1.97 | GPU wake in window |
| light load, turbo off | 8.20 | 2.01 | GPU wake in window |
| light load, turbo on again | 8.21 | 2.01 | GPU wake in window |

- **Refresh rate:** 60 Hz saves nothing at static screen-on idle. The clean pair is within noise, because with PSR the link is idle either way. Keep 240 Hz. Scrolling or video at 60 Hz was not tested.
- **Turbo:** off saves nothing under light bursty load. Keep it on.
- **Contamination:** the periodic NVIDIA GPU wakes (below) put 17–18 W spikes into the later windows. Compare only rows with the same note.

### B27 root cause: the dGPU wakes on every 1% of battery

During the battery A/B, `gpu-wake` logged a resume every ~6 min, each 27–28 s before UPower recorded a 1% drop (23:20:49/23:21:17, 23:26:58/23:27:25, 23:33:03/23:33:31, …). With EC query logging on (`dynamic_debug`: `file ec.c format "Query"`), the next drop showed `_Q3F` (battery status) then `_QB6` at 00:06:31.8, and the GPU resumed at 00:06:34.2. No other EC queries fired in those 6 min.

In the DSDT:
- `_QB6` calls `SPAB (RSOC > 50%)`.
- `SPAB` sets `NPCF.DBAC`/`DBDC` (the Dynamic Boost flags) and sends `Notify (NPCF, 0xC0)` every time, even when the flags didn't change.
- The NVIDIA driver handles the notify in `rm_acpi_nvpcf_notify()`, which takes a dynamic-power reference and so resumes the runtime-suspended GPU.

**Cost:** 22.6 s awake for the wake timed at the 68→67% drop (00:24:08), in line with the boot average of ~25 s (547 s over 22 wakes). That is roughly 7 wakes per hour at 6.5 W. That is an estimated ~0.45 W, ~7% of screen-on idle draw on battery, plus one wake per profile change.

**Upstream:**
- NVIDIA/open-gpu-kernel-modules #1300 reports it; one comment there names the same `_QB6` path on a ProArt P16.
- PR #1299 ("defer NVPCF notifications until runtime resume") has been tested on Zephyrus G16 GU605CP and GA605 units.
- NVIDIA replied that a fix "will be included in a future release" (internal bug 4084236).

**Decision:** don't carry a patched NVIDIA module. It would have to match every `nvidia-utils` update exactly, and a mismatch means no dGPU until it is rebuilt. After each NVIDIA driver update, check the release notes for the NVPCF deferral, then re-measure with `journalctl -t gpu-wake` across a few battery-percent drops.
